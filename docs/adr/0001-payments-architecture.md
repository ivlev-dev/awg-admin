# ADR 0001. Архитектура оплаты тарифов и подписок

- Статус: Proposed
- Дата: 2026-11-16
- Контекст: `docs/PAYMENTS.md`

## Контекст

В системе есть технические тарифы (`tariffs`), привязка `User.tariff_id`,
месячная квота и ограничение `1 kbps` при её превышении. Коммерческого слоя
нет: нельзя выставить счёт, принять оплату, продлить подписку и корректно
ограничить доступ неплательщику. `User.disabled` уже занят административной
блокировкой и не подходит для биллинга.

Платёжный шлюз ещё не выбран. Нужна модель, которая не зависит от конкретного
провайдера и не требует хранения данных карт.

## Решение

1. Выделить bounded context `billing`, который зависит от `tariffs` и
   `identity`, но не наоборот.
2. Разделить `Plan` (коммерческий каталог) и `Tariff` (технические лимиты).
   `Plan` ссылается на `tariff_id`; `Subscription` хранит снимок цены, валюты
   и периода, чтобы изменение каталога не меняло действующий договор.
3. Считать `subscriptions.status` единственным источником истины для доступа:
   `incomplete`, `trial`, `active`, `past_due`, `suspended`, `canceled`.
   `billing_access` — производная проекция для snapshot и UI.
4. Не использовать `User.disabled` для биллинга. Не обнулять `User.tariff_id`
   при приостановке/отмене: доступ блокируется статусом, а тариф сохраняется
   для истории и быстрой реактивации.
5. Блокировать data plane через существующий механизм `1 kbps`: snapshot
   получает `BillingAccess`, выставляет `UserLimit {1,1}` и `DesiredPeer {1,1}`,
   отключает forwarding. API-мутации при блокировке возвращают `402`, но вход,
   чтение и оплата остаются доступны.
6. Оставить квоту календарной (месяц UTC), не привязывая её к периоду
   подписки. Это сохраняет текущее поведение `/quota`.
7. Ввести `Invoice`, `PaymentMethod`, `PaymentEvent`, `DunningAttempt`,
   `SubscriptionEvent`. Деньги — целые minor units. Данные карт не хранятся:
   только токен, brand, last4 и срок.
8. Определить порт `PaymentGateway` (`create_checkout`, `charge_recurring`,
   `refund`, `verify_webhook`, `parse_event`) и `NoopGateway` для dev.
   Все списания идемпотентны; неизвестный результат не повторяется вслепую.
9. Обрабатывать webhook идемпотентно по `(gateway, event_id)`, с проверкой
   подписи, timestamp и хеша тела. Дубликат обработанного события — `200` без
   повторных side effects.
10. Использовать dunning 0/3/7 дней от `due_at`, grace 10 дней, suspend на
    10-й день, write-off/cancel на 30-й. Продление — за 3 дня до конца
    периода; списание — в `due_at`.
11. Поднять схему redb до версии 2, добавить таблицы и индексы
    (`user_id`, `status`, `next_charge_at`/`next_retry_at`), выполнить
    идемпотентную миграцию 1→2 без изменения существующих пользователей.
12. Внедрять поэтапно: модель/БД/read-only API → checkout/webhook → автосписание
    и dunning → UI. По умолчанию биллинг выключен; на этапе 2 включается для
    пилота, на этапе 3 — для автосписания.

## Последствия

Положительные:

- биллинг не ломает текущие тарифы, квоту и worker;
- можно выбрать любой шлюз, реализовав порт;
- нет PCI-данных в системе;
- доступ управляется детерминированно и обратимо;
- схема и API готовы к пилоту до подключения реальных денег.

Отрицательные и риски:

- появляется ещё один контекст, таблицы и фоновые задачи;
- snapshot должен знать о `billing_access`, иначе блокировка не сработает;
- `1 kbps` — мягкая блокировка: конфиги и ключи остаются рабочими;
- отключение биллинга возвращает всех в manual/full, включая отменённых;
- нужны billing-шаблоны писем; email у пользователя уже есть, транспорт
  `log`/`smtp` реализован в `admin::mailer`;
- миграция v2 несовместима с restore backup v1 без старого бинарника.

## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| `User.disabled = true` при неоплате | блокирует вход и оплату, смешивает админ- и биллинг-блокировки |
| Обнулять `User.tariff_id` | теряются лимиты/история, квота становится unlimited, сложная реактивация |
| Хранить карты у себя | PCI DSS, ненужный риск |
| Внешний биллинг-сервис как источник истины | дополнительная система и синхронизация; можно вернуться позже |
| Списывать заранее за 3 дня | усложняет dunning 0/3/7; выбран только ранний счёт |
| Привязать квоту к периоду подписки | ломает текущий календарный `/quota` и статистику |

## Открытые вопросы

- шлюз, юрлицо, юрисдикция и валюты;
- НДС/чеки 54-ФЗ и фискальные поля;
- нативная рекуррентность vs токены/off-session;
- proration при смене плана;
- канал и согласие на dunning-письма (email уже есть, Telegram — опционально);
- хранение фискальных данных покупателя и GDPR-retention;
- Telegram Stars: актуальная поддержка подписок и возвратов.
